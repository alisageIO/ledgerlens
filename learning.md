# Learning Points & Architectural Patterns

Here are critical lessons and patterns discovered during the implementation of the LedgerLens backend features.

## 1. Idempotent Database Migrations in SQLAlchemy / Alembic

### Context

In microservices or systems where multiple environments (local tests, staging, production) might have databases in different states of sync, migration failures are common. For example, if a table was created directly (e.g., via `Base.metadata.create_all` in a local test suite run) but the migration system tries to run a standard autogenerated `CREATE TABLE` migration, the migration system will crash.

### Pattern

Instead of raw `CREATE TABLE` and `DROP TABLE` statements, migrations can be made **idempotent** by using SQLAlchemy’s schema reflection (`sa.inspect`).

#### Upgrade (`up`) Guard

```python
def upgrade() -> None:
    bind = op.get_bind()
    inspector = sa.inspect(bind)

    if "users" not in inspector.get_table_names():
        op.create_table(
            "users",
            sa.Column("id", sa.Uuid(), nullable=False),
            # ... columns
        )
```

#### Downgrade (`down`) Caution & Schema Ownership

Unconditional downgrade guards (like dropping a table solely because it exists) create a critical mismatch if the `upgrade()` step skipped table creation because the table was pre-existing (e.g. created by test runs or legacy scripts). If a downgrade is subsequently run, it would drop a table it did not actually create or own, causing data loss or breaking other dependencies.

Therefore, migrations must establish explicit schema ownership:

1. **Never drop objects unless you are certain they were created by this migration.**
2. If pre-existing tables exist, resolve them via a separate preflight/repair migration or schema synchronization script before running subsequent migrations, rather than letting migrations silently record success for an inherited table.

### Why Option A over Raw SQL

Using the inspector-based checking (`sa.inspect`):

1. Keeps migrations dialect-agnostic (SQLAlchemy handles translation to SQLite, Postgres, MySQL, etc.).
2. Avoids executing raw SQL wrapper logic for enums or indexes.
3. Integrates naturally into Python-based migration systems like Alembic.
